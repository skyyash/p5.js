Stop 1 · The 4-line key — shaderHookUtils.js

getShaderHookTypes parses a hook signature into parameter info. It only searched vertex/fragment; compute hooks live under hooks.compute, so buildComputeShader died on WebGL with Can't find hook iteration!. The WebGPU renderer's own version already searched compute; this mirrors it:

if (!body) {
  body = shader.hooks.compute[hookName];
  fullSrc = shader._computeSrc;
}
⏸ Predict: our hook is spelled (ivec3 index) but WebGPU's is (index: vec3<i32>). Why can't we reuse the same string?
Different parsers: the WebGL one splits parameters on whitespace as type name; WebGPU's splits on : as name: type. Same hook, two shader languages. With the WGSL spelling, the WebGL parser reads type index: and the hook resolves to garbage.

Stop 3 · Keeping the IR — p5.strands.js

const cpuIR = isComputeShader
  ? { dag, cfg, uniforms: [...uniforms], hooks: [...hooks] }
  : undefined;
const modified = oldModify.call(this, hooksObject);

What modify() normally does, step by step. When you write buildComputeShader(() => { ... }), your callback never runs as real logic. modify() (in src/strands/p5.strands.js) does three things: (1) transpile your function source into interceptable JS, (2) record it by executing that JS with every p5 operation (like +, sin(), d[i]) replaced by a function that builds a graph node instead of computing a value, (3) generate shader text from that graph via generateShaderCode() and hand it to the old modify (oldModify) which installs real hook functions. Then it calls deinitStrandsContext(), which wipes the DAG, CFG, uniforms, and hooks clean for the next shader.

Recording vs executing. This is the single most important idea. If your callback says let x = a + b, no addition happens at record time. Instead a + b creates an OPERATION node meaning "add these two inputs", and x becomes a handle (a StrandsNode wrapping a numeric node ID). The actual addition happens later, either on the GPU (compiled WGSL/GLSL) or, new in this branch, in JS by the CPU backend replaying the graph. That is why the quiz says the callback body executes zero times as logic.

The four pieces, concretely. dag (directed acyclic graph) is the math: every value node (literals, variables, a+b, d[i] reads) plus which nodes each one depends on. "Acyclic" just means values flow one way, no loops at the value level; loops live elsewhere. cfg (control-flow graph) is the order: a list of basic blocks (GLOBAL, FUNCTION entry per hook, IF_COND, FOR, SCOPE_START/END, BRANCH) plus edges between them and the statement IDs recorded in each block. uniforms is the inputs table: every uniformStorage() / uniformFloat() call pushes {name, typeInfo, defaultValue}, where defaultValue is either the buffer or a function returning it. hooks is the entry-point table: one entry per hook with entryBlockID (which CFG block to start compiling from), rootNodeID, hookType, and shaderContext: 'compute'. Without hooks the backend would not know where the compute body starts; without uniforms it could not resolve buffer names to actual CPU objects.

Reading the diff line by line. isComputeShader = this.shaderType === 'compute' gates everything so render shaders pay nothing. dag and cfg are stored by reference (they are dead after deinit anyway, so no copy is needed). uniforms: [...uniforms] and hooks: [...hooks] make a shallow array copy, meaning a new array holding the same entry objects, because deinit resets ctx.uniforms = [] which would otherwise orphan nothing but is still safer to snapshot. Finally modified._cpuIR = cpuIR attaches the stash to the returned shader object, which is what runCpuCompute() later reads as shader._cpuIR. If it is missing, you get the "missing recorded program" internal error.

Why render shaders are excluded. Two reasons: memory (every render modify() would otherwise retain a full graph forever) and risk (the CPU backend only understands the compute hook; stashing render IR would suggest it can run it, which it cannot). The ternary makes this a zero behavior change for all existing material, filter, and color shaders.

⏸ Predict: why stash all four (dag, cfg, uniforms, hooks) instead of just the graph?
dag/cfg hold math and order, but buffer bindings and defaults live in uniforms, and the hook's entry block ID lives in hooks. The driver needs every one: entry block to start compiling from, uniforms to resolve values. Concretely, compileCpuComputeHook() does cpuIR.hooks.find(h => h.shaderContext === 'compute') to get entryBlockID, walks cfg from there with sortCFG, evaluates dag nodes into JS strings, and looks up every storage/scalar name in uniforms.

Stop 4 · One extra field — strands_api.js

What uniformStorage(name, bufferOrSchema) does. It does not copy data. It declares "this shader reads a buffer called name" by creating a VARIABLE node with baseType: 'storage' and pushing {name, typeInfo, defaultValue} onto ctx.uniforms. defaultValue is the buffer itself, or the function you passed (e.g. () => cells), which is re-called every compute() so buffer swaps take effect. typeInfo carries schema (struct field layout, or null for plain numbers), isStorageList, maxCapacity, and now arrayType.

What arrayType is and where it comes from. CPU/GPU buffers hold numbers in typed arrays: Float32Array, Int32Array, or Uint32Array. Each buffer object stores its constructor as _arrayType. The new code reads value?._arrayType?.name and maps it to the string 'float' | 'int' | 'uint' (defaulting to 'float' for plain JS arrays, which createStorage treats as float). This string rides along on typeInfo.arrayType inside the uniforms entry stashed in Stop 3.

Why the render path needs it but WGSL does not. On WebGPU, a storage buffer has a real integer type, so an int buffer read is already an int. On WebGL, the render-path replacement is a data texture (Stop 6), and textures only store floats (RGBA32F). So every fetch comes back as float, e.g. texelFetch(data, ...).r. If your shader then does integer math or passes the value somewhere expecting int, GLSL refuses to compile because GLSL is strictly typed: float does not implicitly become int. The fix in generateStorageRead() (strands_glslBackend.js) is a wrapping cast: int(fetch.r) for int buffers, uint(fetch.r) for uint buffers, plain fetch.r for floats. The WGSL backend simply never reads this field, which is why the diff comment says it is ignored there.

Common confusion: this affects reads, not writes. The compute shader itself runs on the CPU (Stop 5) against the real typed array, so integer semantics are already correct there (Math.trunc for int division, real ints in the array). arrayType only matters when a render shader (material/filter, running on the GPU) reads CPU-computed data through the texture. That is also why scalar struct fields with dim > 1 do not need it: vectors are always float in this codebase.

Stop 5 · The JS backend — strands_jsBackend.js (new)

The big idea: compile once, run many times. The alternative the issue considered was interpreting the IR: walk the DAG/CFG node by node for every index, every compute(). That works but repeats graph traversal N times per dispatch. Instead compileCpuComputeHook(cpuIR) translates the whole compute hook into one JS function once per shader (cached as shader._cpuComputeFn) shaped like fn(__idx, __s, __u, __v, H), then runCpuCompute(shader, x, y, z) calls it in a plain loop, once per index. new Function(body) is used the way shader compilation uses compileShader: the generated source string becomes an executable function. Dump it with console.log(shader._cpuComputeFn.toString()) when debugging; the let t = t bug was found exactly this way.

How control flow becomes JS. sortCFG(outgoingEdges, entryBlockID) returns blocks in an order the GLSL backend already proved correct, so the JS backend reuses the same structure: emitRange() walks the sorted list and writes if / else if / else chains for IF_COND/ELSE_COND runs, for (init; cond; update) for FOR blocks, and { } for SCOPE_START/END. BRANCH blocks pre-declare phi temporaries (let t;), loop bodies assign them per branch (assignPhiNodeValues). A phi node is compiler jargon for "this variable has a different value depending on which branch ran, so merge them here"; straight-line code like let n = 0; n = n + 1 needs no phi, which is why quiz Q3 works with plain rebinding. Mirroring the GLSL handlers handler-for-handler is deliberate: any fix to ordering logic only needs to be reasoned about once.

How values work: the value model and environments. JS has one number type, but GLSL distinguishes float, int, bool, and vectors. The backend emulates GLSL: scalars are JS numbers/booleans, vectors are plain JS arrays (e.g. vec3(1,2,3) becomes [1,2,3] via H.vec()), scalar-vector ops broadcast (adding 1 to [1,2,3] adds to each element), int division truncates (Math.trunc(a/b)), and float % becomes mod() (a - b*floor(a/b), which differs from JS % for negatives). Every identifier compiles to an environment lookup, never a bare JS variable: __s["buf"] is a storage buffer object, __u["speed"] is a scalar uniform, __v["myVar"] is a shader local, __idx is the current (x,y,z) index array. This means user names can never collide with generated __t0 temporaries, and rebinding a buffer under the same uniform name just changes what __s points to.

H: the single choke point. All runtime behavior lives in the helpers object passed as H: H.vec/binop/unop/swiz/swizSet for values, H.readFieldValue/writeFieldValue for struct fields (converting between stored p5.Vector/p5.Color/array/number and plain math values), and H.call(name, args) for every builtin (sin, mix, dot, etc. implemented with Math.*). Two special cases: random() is a deterministic hash of (seed, flatIndex, callCount), documented as approximate, not bit-identical to the GPU; noise() calls the real p5.noise() after temporarily applying the shader's noiseDetail() octaves/falloff and restoring them in a finally. Storage-list ops compile to H.pushList/H.lenList/H.popList plus H.makeStruct. If you add a new builtin, H.call is the only place to touch.

The driver: runCpuCompute(shader, x, y, z). It validates the shader is a compute shader, errors if _cpuIR is missing, computes total = x*y*z, warns (not caps) past 4096 items because silently dropping cells would corrupt simulations like Game of Life, then: (1) resolve stores once via resolveStores(): call function initializers (this is why the [nextCells, cells] = [cells, nextCells] swap keeps working, each dispatch re-resolves), then apply setUniform() overrides; (2) resolve scalars once via resolveScalars(), converting p5.Vector/Color to plain arrays with toPlainValue(); (3) loop flat = 0..total-1, mapping back to (x,y,z) with ix = flat % x; iy = floor(flat/x) % y; iz = floor(flat/(x*y)) (try the widget below), resetting randomCalls and passing a fresh {} locals object per invocation so iterations cannot leak state; (4) bump every bound store's _cpuVersion afterwards, because kernel writes mutate raw arrays/objects directly with no setter call, and the texture uploader (Stop 6) relies on the version to know to re-upload.

⏸ Predict: in the doubling example the read d[idx] and the write target d[idx] are two different IR nodes with identical inputs. Why duplicate instead of reuse?
Reads and writes need different node identities: the read is a value (an OPERATION producing data), the write target anchors an ASSIGNMENT. Sharing one node would conflate "compute this value" with "store to this location" — and the write-side node isn't even recorded as an instruction, only the assignment is.

Stop 6 · Data textures — cpuStorageTexture.js (new)

The problem: two processors, one dataset. After Stop 5, compute results live in plain JS memory (typed arrays, object arrays). But material and filter shaders still execute on the GPU, which cannot read JS memory directly. The bridge is a data texture: the CPU packs buffer contents into a floating-point image, uploads it with texImage2D, and the render shader reads values back with texelFetch (Stop 7). No user code changes; uniformStorage() names keep working on both paths.

Layout, with a worked example. Format is RGBA32F: each texel (texture pixel) holds 4 x 32-bit floats (r,g,b,a). Width is fixed at 256 texels, so any element index i maps to 2D coordinates with shader-only math: x = i % 256, y = i / 256 (integer division). A scalar list uses one texel per element, value in red (pixels[i*4] = value). A struct packs each field into whole texels: texelsPerField = ceil(dim/4), so a vec3 position (dim 3) takes 1 texel, a hypothetical dim-5 field would take 2. Fields get baked integer offsets from the schema in order, and stride = total texels per element. Example: {position: vec3, velocity: vec3} gives offsets 0, 1 and stride 2; element e's velocity starts at texel e*2 + 1, channels .rgb. cpuStorageLayout() computes {fields, stride, count, width, height} and packCpuStorage() fills the Float32Array; fieldComponents() knows how to read numbers, plain arrays, p5.Vector (.x/.y/.z), and p5.Color (_getRGBA()).

Why stride and count are uniforms, not constants. The GLSL in Stop 7 bakes field offsets as literals (they come from the schema known at codegen time) but reads stride from uniform int <name>_stride and list length from uniform int <name>_count. Reason: you can rebind a different buffer under the same uniform name (or push to a list, changing its length) without rebuilding the shader. _updateTexture() / _setCpuStorageLayoutUniforms() in p5.RendererGL.js upload the fresh numbers every draw. If stride were baked, rebinding a differently-shaped buffer would silently read the wrong texels.

The uploader: CpuStorageTexture. It deliberately implements the exact interface the existing sampler path expects: bindTexture() (create-once + bind a TEXTURE_2D) and update() (re-upload only if buffer._cpuVersion !== _uploadedVersion). Instances are cached per renderer in renderer.textures via cpuStorageTextureFor(), so repeated binds are cheap. Filtering is NEAREST (exact texels, no blending) and wrap is CLAMP_TO_EDGE. The premultiply guard from the quiz (pixelStorei(UNPACK_PREMULTIPLY_ALPHA_WEBGL, false) around the upload, restoring the old value after) exists because p5 leaves premultiplying on after text drawing, which would multiply RGB by alpha 0 and zero out scalar payloads sitting in red.

⏸ Predict: uploads rendered black with no GL error until one pixelStorei guard was added. What was it and why?
p5 leaves UNPACK_PREMULTIPLY_ALPHA_WEBGL on outside text drawing. A scalar list packs its value into red with alpha 0, and premultiplying zeroes RGB by alpha. The upload now disables premultiply around texImage2D and restores the previous value. Silent data corruption with no error flag — the nastiest kind.

Stop 7 · GLSL render path — strands_glslBackend.js

Declarations: turning a buffer name into samplers. addStorageBufferBindingsToDeclarations() runs at codegen time for every storage uniform: it adds uniform sampler2D NAME; plus uniform int NAME_stride; (and uniform int NAME_count; for lists) to both vertex and fragment declarations. A sampler2D is GLSL's handle for "a texture I can fetch from"; the stride/count uniforms are filled per draw as described in Stop 6. The first thing the function checks is whether the shader has any vertex/fragment hook (shaderContext === 'vertex' || 'fragment'). Compute-only shaders return early: their GLSL is generated but never compiled on the CPU path, so declaring samplers for them would be dead code at best and a confusing error source at worst.

Reads: from d[i] to texelFetch. In the IR, every storage read is an ARRAY_ACCESS node (buffer, index, plus an optional field name for structs). generateStorageRead() matches only when the buffer resolves to a storage uniform via storageInfoOf() and the current stage is not compute; otherwise it returns null and the legacy path runs. The emitted code uses texelFetch(sampler, ivec2(x, y), 0), which is WebGL2/GLSL3's "give me the exact texel at integer coordinates, no filtering" primitive (plain texture() would interpolate, which would corrupt data). Scalar element i becomes texelFetch(n, ivec2((int(i)) % 256, (int(i)) / 256), 0).r: index to 2D coords, take red. Struct field f of element i becomes (i * n_stride + OFFSET) as the linear texel, with a channel swizzle (.r for float, .rgb for vec3, multi-texel assembly for dim > 4). Offsets are counted by summing ceil(dim/4) over preceding schema fields, mirroring cpuStorageLayout() exactly; if the two ever disagree, reads silently land on the wrong texel, so keep them in sync.

Two deliberate errors. (1) WebGL1 has no texelFetch, so render-path reads fail fast with "needs WebGL2" while compute() itself keeps working on the CPU; the alternative would be cryptic link errors. (2) push/pop inside a render shader fail loudly (generateStorageListCall throws "cannot be used in vertex/fragment"), because appending from a parallel render pass has no sensible meaning; length instead compiles to the (NAME_count) uniform read, which is safe. Scalar int/uint reads get the int()/uint() wrap from Stop 4 here, at the wrapScalar step.

Stop 8 · Instances and tests — 3d_primitives.js, p5.RendererGL.js suite

What instancing is. model(geometry, count) draws many copies of one shape in a single draw call; inside the shader, instanceIndex (0, 1, 2, …) tells each copy which data element to read, e.g. let item = data[instanceIndex]. On WebGPU, count can itself be a GPU storage list whose length is only known on the GPU, so p5 uses an indirect draw path (_instanceList): the GPU reads the count buffer to decide how many instances to launch.

The CPU shortcut. A CpuStorageList is a plain JS array, so list.items.length is known synchronously on the CPU. The instances() change in 3d_primitives.js checks count._isCpuStorage: if set, it takes the plain _instanceCount = list.length path (a normal instanced draw with a numeric count) instead of the indirect path. Same pixels, far less machinery, and no GPU-readable count buffer needed. Plain numbers still work exactly as before.

What the 21 tests cover, grouped. (1) Storage API parity: count/array/typed/struct creation, read returns copies, update/set/push/pop/clear validation and bounds errors, int vs float preservation. (2) Compute correctness: the doubling kernel (d[idx] = d[idx] * 2), index mapping with 1D and 2D dispatch, function-form uniforms (() => buf re-resolved per dispatch, incl. the swap trick), branches and loops, Game of Life blinker one-step, a particle update, list push + length from inside the kernel. (3) Driver behavior: >4096 dispatch warns but runs everything. (4) Render integration: filter-shader pixel output from CPU data, per-instance struct display, list-driven instancing. If you break something, run this suite first; the test names map one-to-one onto the stops above.

Two infra lessons from debugging: create canvases inside setup() (p5's async startup installs a default P2D canvas that replaces any canvas made earlier at module scope, so a beforeEach that sees RendererGL can still hand the test a Renderer2D; making the canvas in setup() runs after startup settles). And instance-mode shader callbacks need { myp5, ...vars } scope objects: the transpiler resolves free names through the scope you pass, so omitting it makes every name resolve to nothing.

Calibration quiz

Pick one. Explanations appear after you answer; score updates above.

Q1. You call buildComputeShader(simulate) then compute(s, 100) on WebGL. How many times does the body of simulate execute on the CPU?

B. The function is never "run" as logic; executing it while recording only constructs IR nodes. At compute() time the compiled JS from that IR runs instead. This is why a plain for loop over the callback could never work.

Q2. uniformStorage(() => cells) passes a function. When is it called on the CPU path?

C. Like GPU uniforms, values resolve per dispatch — which is exactly why the [nextCells, cells] = [cells, nextCells] swap trick keeps working: each compute() re-resolves to the current bindings.

Q3. In the Game of Life test, plain let n / alive / out locals need no declarations or phi nodes in the generated code. Why?

A. Plain JS rebinding just points the variable at a newer node; only values that merge across branches (phi) or cross into storage need explicit handling. Straight-line scalars evaluate and vanish.

Q4. Why warn instead of cap when dispatch exceeds 4096 items?

B. A cap changes results without telling anyone. Warn-and-run preserves correctness; reducing item counts belongs in examples/docs, visibly.

Q5. filter(displayShader) with uniformStorage inside failed with a clear error before the render path landed. Which layer produced it, and why was a clear error the right call?

C. Without a binding, codegen would emit references to undeclared identifiers and die deep in GL compile logs. Failing fast at codegen with the reason attached is strictly better. (Now replaced by the texture path.)

Q6. Your filter test failed with all-black output, but the bug was a missing filterColor.end() in the test. What does that teach about hooks?

A. No finalize, no hook entry, no error — the base shader renders as if you never called modify. Silent no-ops like this are why the walkthrough says: when output looks "default", check your begin/end pairing first.

War stories (how each bug was actually found)

1. The method exists but the guard throws

RendererGL had createStorage, yet tests threw "WebGPU only". Probing showed beforeEach saw RendererGL while the test saw Renderer2D: p5 installs a default P2D canvas during async startup, replacing the earlier canvas. Fix: create canvases in setup(). Lesson: when the object is right in one place and wrong in another, suspect lifecycle, not logic.

2. let t = t

Temps self-referenced because the name was recorded before emitting the expression, so lookup returned the name itself. The GLSL backend emits first and names after. One-line fix, found by dumping the generated function.

3. Loops that never loop

Two codegen loops tested sorted.length on a {blocks, types} wrapper — always undefined, so branch/scope discovery silently did nothing. No error, just wrong code. Lesson: wrappers without .length fail open in comparisons.

4. Black textures, no GL error

Upload, binding, shader, and fetch all verified correct — yet black. Root cause was host-side pixel-store state (premultiplied alpha), invisible to every GL check. Lesson: when the GPU pipeline is proven right piece by piece, look at the state around the calls.

5. The missing end()

An all-black filter test triggered a deep investigation (transpiler! hooks! codegen!) before anyone noticed the test itself never called end(). The framework behaved exactly as designed — silently rendering the default hook. Lesson: reproduce with the smallest possible input (constant white) before theorizing.

Glossary

IR
Intermediate representation: the recorded form of the shader callback, split into a DAG (math) and CFG (order).
DAG
Directed acyclic graph of value nodes (literals, variables, operations). Sharing inputs is fine; read/write positions need distinct nodes.
CFG
Control-flow graph of basic blocks (default, if_cond, for, scope, merge…). Determines execution/generation order.
PHI
A node merging values from different branches (declared in BRANCH blocks, assigned at branch ends).
Hook
A named injection point in a shader (e.g. filterColor, iteration); begin/end bracket recording.
Backend
Turns IR into executable form: WGSL/GLSL text, or (new) a JS function.
uniformStorage
Binds a storage buffer/list into a shader; accepts a buffer or a function returning one (re-resolved per dispatch).
texelFetch
GLSL3 direct texel read by integer coordinates — the primitive behind render-path storage reads.
stride / count
Dynamic uniforms describing packed texture layout (texels per element; live list length).
