CPU Fallback Lab Manual — Rebuild It Yourself

Derived backwards from feat/cpu-fallback-compute. Start on a clean checkout of upstream/main and rebuild the whole feature lab by lab.

Rule per lab: read first, write second, verify third. When it breaks (it will), read the When it breaks box last, not first.

Lab 0 · Workbench and first red

goal A branch, a passing baseline, and one failing test that proves the gap.

Do

  1. Create your lab branch from upstream tip: 
    git fetch upstream main
git checkout -b lab/cpu-fallback upstream/main
  2. Confirm the baseline builds and the WebGL suite passes: 
    npm run build
npx vitest run test/unit/webgl/p5.RendererGL.js --project unit-tests
    Expect 191 passed. If this fails, fix your environment before continuing — nothing else will make sense on a broken bench.
  3. Create test/unit/webgl/cpuComputeFallback.js with the standard harness (instance in beforeEach, canvas inside setup() — see the trap below), and write exactly one test: createStorage([1,2,3]) on a WEBGL canvas. Run just your file and watch it go red with only available with the WebGPU renderer.
⏸ Harness trap: your first version will likely create the canvas in beforeEach and see a Renderer2D in tests. Why?
p5 installs a default P2D canvas during async startup (#_setup in src/core/main.js), which replaces anything created before it finishes. The repo's own tests create canvases per-test (after async hook boundaries) for exactly this reason. Canonical fix: create the canvas inside the sketch's setup(), which runs after the default exists.
Done when: baseline green, your one test red with the WebGPU-only error. Read src/core/p5.Renderer3D.js guards (createStorage, buildComputeShader, compute) and note the shared shape: throw unless the renderer implements it. That shape is your whole assignment: implement it on the renderer.

Lab 1 · CPU storage mirror

goal createStorage works on WebGL. read RendererWebGPU.createStorage + StorageBuffer constructor.

Do (in this order — do not skip ahead)

  1. 1a — numbers. Add CpuStorageBuffer (fields: _isStorageBuffer = true, data, length, _schema, _arrayType) and RendererGL.createStorage handling only number → zero-filled Float32Array and float arrays (copy, never alias). Add update, read (copies!), set with bounds checks. Test: lengths, read-back values, update then set.
  2. 1b — structs. For arrays of objects, store them as-is and infer a schema. Required shape per field: {name, dim, kind} where kind is number | array | vector | color.
    ⏸ Stuck on the schema shape? First try the "obvious" {fields: ['position', …]}, run a struct test, and read the crash before revealing. 
    function inferCpuStructSchema(firstElement) {
  const fields = Object.entries(firstElement).map(([name, value]) => {
    if (typeof value === 'number') return { name, dim: 1, kind: 'number' };
    if (Array.isArray(value)) return { name, dim: value.length, kind: 'array' };
    if (value?.isVector) return { name, dim: value.dimensions ?? 3, kind: 'vector' };
    if (value?.isColor) return { name, dim: 4, kind: 'color' };
    throw new Error(`createStorage() field "${name}" must be a number, an array of numbers, a p5.Vector or a p5.Color.`);
  });
  return { fields };
}
    The strings-only version breaks because createStructArrayElementProxy (ir_builders.js) builds one getter per field using field.name and sizes IR nodes with field.dim. With strings, no getter exists, d[i].position is undefined at record time, and primitiveConstructorNode crashes on a.isStrandsNode.
  3. 1c — lists. Add CpuStorageList (maxCapacity, items, length getter, push/pop/clear/update/read) and createStorageList mirroring the WebGPU branching (struct array → schema + items; plain object → schema only; empty → float list).
Done when: count/array/typed/struct storage plus float and struct lists round-trip through read/update/set/push/clear, overflows throw, and reads return copies. Key file to compare against afterwards: the final CpuStorageBuffer/CpuStorageList in p5.RendererGL.js.
Takeaway: everything downstream keys off duck-type flags (_isStorageBuffer, _schema), not classes. Get the flags right and uniformStorage() accepts your objects untouched.

Lab 2 · Make buildComputeShader stop throwing

goal buildComputeShader(() => {}) returns on WebGL. read RendererWebGPU.baseComputeShader, the Shader constructor's compute detection, and both hook-type parsers.

Do

  1. Add RendererGL.baseComputeShader() returning new Shader(this, 'void main() {}', {compute: {'void iteration': '(ivec3 index) {}'}}). The source is never compiled on this path; it only gives modify() hook type information.
  2. Fix getShaderHookTypes in shaderHookUtils.js to also search hooks.compute (4 lines, mirrors WebGPU).
  3. Verify shader.hookTypes('void iteration') resolves instead of throwing Can't find hook.
⏸ Predict first: why must our hook say (ivec3 index) when WebGPU's says (index: vec3<i32>)?
Two parsers, two languages. The WebGL one splits parameters on whitespace as type name; WebGPU's splits on : as name: type. Feed ours the WGSL spelling and it reads type index: — garbage in, garbage out. If you hit this wall, you now know exactly which file to open.
Done when: no more only available with WebGPU from buildComputeShader; the failure (if any) moved deeper into modify, which is progress. Deliberately do not touch compute() yet.

Lab 3 · Stash the IR, run one hardcoded op

goal compute() runs d[i] = d[i] + 1 on the CPU. read p5.strands.js modify() (3 phases), ir_types.js node/opcodes.

Do

  1. In modify(), after generateShaderCode, stash {dag, cfg, uniforms, hooks} on the returned shader — compute shaders only. Everything else must behave byte-identically.
  2. Add RendererGL.compute(shader, x, y, z) that finds the first storage uniform and runs a hardcoded +1 loop. Test [1,2,3] → [2,3,4].
  3. Dump one real IR (log nodeTypes/opCodes/dependsOn for the doubling shader). Find the read node, the write-target node, the multiply, and the assignment. Notice read and write are different nodes with the same inputs — values vs store locations need distinct identities.
Takeaway (the big one): your callback body runs zero times as logic. Executing it only constructs IR nodes ("fake JS"). That is why looping over the callback could never work, and why every later lab reads the stashed IR instead.
Done when: the +1 test passes and you can point at each of the 4 node kinds in the dump. The hardcoding is intentional scaffolding — Lab 6 removes it.

Lab 4 · Real index, struct fields

goal Replace the cheat with index.x and data[i].position. read ir_builders.js array access + struct proxy, webgpu/shaders/compute.js index mapping.

Do

  1. Index. Change the loop to compute ix = flat % x (plus iy/iz for later) and store ix. Test shader: d[i] = index.x on [0,0,0] → expect [0,1,2]. Rebuild before reloading (index.html loads the built bundle, not src).
  2. Structs. Branch on buf._schema: for struct items do component-wise position += velocity (mind p5.Vector vs plain arrays). Test one particle (0,0)+(1,2) → (1,2).
  3. Look, don't leap. Log dag.nodeTypes/opCodes/dependsOn for both shaders and identify ASSIGNMENT, ARRAY_ACCESS (note identifier: 'position' on struct access), and ADD.
Done when: float-index and struct-particle tests both pass. You still hardcode two shapes — Lab 5 adds two buffers and control flow, Lab 6 deletes all hardcoding.

Lab 5 · Game of Life, still hardcoded

goal Run the docs' blinker on CPU. read Shader.setDefaultUniforms (initializer resolution is the pattern to copy).

Do

  1. Resolve like the GPU path. At the top of compute: storage entries may be buffers or functions returning them — call functions. Same for scalar uniforms. Log the resolved names for a 4×4 test before doing any math.
  2. Threshold first (no loops). Shader: if (cur[i] > 0.5) nxt[i] = 1 else 0 on [0, 0.8, 0.2] → [0, 1, 0].
  3. Blinker. Hardcode neighbor counting with wraparound on 4×4 (horizontal row → vertical column in one step). Compare against a hand-computed expectation.
⏸ Two design questions before you continue: (1) when dispatch exceeds ~4096 items, cap or warn? (2) where must resolution happen for the [a,b]=[b,a] swap trick to keep working?
(1) Warn, never silently cap. Dropping invocations corrupts simulations that need every cell; reducing counts belongs visibly in examples/docs. (2) Resolution must happen per compute() call (like GPU uniforms), never cached across frames — the swap rebinds buffers between dispatches.
Done when: threshold and blinker pass. Notice the discomfort: every new shader needs a new hardcoded branch. That discomfort is Lab 6's motivation — say it out loud before continuing.

Lab 6 · Delete the hardcoding: lower IR to JS once

goal One compiler handling every shader so far, in new file src/strands/strands_jsBackend.js. read strands_glslBackend.js end to end first — you will mirror it handler for handler.

Do (smallest working slices — keep every previous test green throughout)

  1. 6a — expressions. Write emitExpression for LITERAL, VARIABLE (index → arg, stores → __s, scalars → __u, everything else → __v locals), ARRAY_ACCESS, SWIZZLE, TERNARY, binary ops via one H.binop helper (broadcasting, truncating int division, float mod), and CONSTRUCTOR via H.vec. Convert the +1 test to use it.
  2. 6b — statements and blocks. Mirror the GLSL cfgHandlers: default/branch/if/for/scope/merge, phi declare-in-branch plus assign-at-branch-ends, for(init; cond; update) from recorded header nodes. Convert threshold + blinker tests. Sort with the existing sortCFG from the hook entry block.
  3. 6c — builtins and lists. One H.call dispatch (Math family, mix/clamp/step, vector ops), random as a seeded per-invocation hash (document: approximate, not bit-identical), noise via real p5.noise with detail save/restore, list push/pop/length, struct constructors from schema field order. Textures throw a clear error.
  4. 6d — driver. runCpuCompute: reject non-compute shaders (same message as GPU), resolve stores/scalars, compile once and cache on the shader, warn past 4096, loop flat→(x,y,z) with fresh locals per invocation, bump all store versions after.
⏸ You will hit at least two of these three; predict the fixes before revealing: (a) let t = t self-reference, (b) branch discovery silently doing nothing, (c) struct reads coming back empty.
(a) Record the temp name after emitting its expression — exactly the GLSL backend's ordering. (b) The sorted list is a {blocks, types} wrapper with no .length; comparisons against it are always false, so loops "never run" with zero errors. Use sorted.blocks.length. (c) Field descriptors need dim (Lab 1 comes back to haunt you) — thread it from schema through emission into the read helper.
Done when: every Lab 3–5 test passes with zero shader-specific branches in compute, plus random/noise smoke coverage. Compare your file against the reference implementation last, not first.
Takeaway: "lower once to JS" beats "interpret per invocation" because the GLSL backend already proved the emission order is a valid structured linearization — you get control flow for free by mirroring it.

Lab 7 · Let render shaders read CPU data

goal The docs' display patterns work unchanged on WebGL. read the sampler flow: getTexture → uniform.texture → bindTextures → _updateTexture, and the _webGL2CompatibilityPrefix (#version 300 es).

Do

  1. Pack. New cpuStorageTexture.js: fixed width 256 (coordinates need no extra uniforms), one texel per scalar, texel-aligned struct fields, dynamic stride/count uniforms for rebinding. Pure functions first — unit-test pack in Node, no browser needed.
  2. Upload. CpuStorageTexture with the bindTexture()/update() interface, cached per renderer, re-upload on version change.
    ⏸ Deliberate trap (do this!): upload without touching pixel-store state, run a filter test, and observe all-black output with zero GL errors. Then reveal.
    p5 leaves UNPACK_PREMULTIPLY_ALPHA_WEBGL on outside text drawing. Scalar lists pack values into red with alpha 0, so premultiplying zeroes the data on upload — silent corruption. Guard with save/set-false/restore around texImage2D. When the GPU pipeline is proven right piece by piece, suspect host-side state around the calls.
  3. Emit. In the GLSL backend: sampler + stride/count declarations for render-stage shaders only (compute-only shaders skip — their GLSL is never compiled), texelFetch reads, length → (name_count), loud errors for push/pop in render shaders and for WebGL1 (no texelFetch; compute fallback still works there).
  4. Bind. getTexture override routes CPU storage to cached data textures; _updateTexture writes stride/count on the current program (locations cached per program); instances() sends CPU lists down _instanceCount.
  5. Prove it with pixels. Filter test: 4×4 cells, one alive cell, assert white and black pixels exist. Material test: per-instance struct positions with a finalColor override to pure red (unambiguous vs background), assert red exists.
Done when: both pixel tests pass. If a render test fails, first check your begin/end pairing — a missing end() silently renders the default hook with no error, which looks exactly like "my feature is broken".

Debugging dojo — five symptoms, you diagnose

For each: state your hypothesis before opening hint 1, then hint 2, then the answer. These are the real failures from building this feature.

Case 1. Tests throw only available with the WebGPU renderer although the renderer has the method — and a probe in beforeEach agrees, while the test body sees Renderer2D.
Something replaces the renderer between setup and test. What does p5 create during async startup?
…a default P2D canvas (#_setup), which clobbers anything created before it finishes.
Create canvases inside setup(). Lesson: right-object-here, wrong-object-there means lifecycle, not logic.
Case 2. Generated code throws Cannot access '__t0' before initialization.
Read the first emitted declaration line literally. What does the right-hand side reference?
Itself — the temp name was recorded before emitting, so lookup resolved to the name being defined.
Emit first, name after — the GLSL backend's ordering. Lesson: compare against the reference implementation operation by operation.
Case 3. Branches and loops silently generate straight-line code — no errors anywhere.
The discovery loops "never run". What do they iterate over, and does that object have the property they test?
They test sorted.length on a {blocks, types} wrapper — undefined, so every comparison is false.
sorted.blocks.length. Lesson: wrappers without .length fail open; prefer explicit shapes.
Case 4. Correct declarations, correct fetch, bound texture, uploaded data, zero GL errors — all-black output.
Every GPU-side fact checks out. What host-side state touches the upload path?
Pixel-store state: p5 leaves alpha-premultiplying on, and scalar data packs into red with alpha 0.
Disable premultiply around the upload, restore after. Lesson: silent host-side corruption beats every GPU-side theory — isolate with a raw (non-strands) shader first.
Case 5. A filter test renders the default hook (passthrough) with no errors, after a long investigation of the transpiler, hooks, and codegen.
Reproduce with the smallest possible input: does a constant-white filter work?
Yes — so the framework is fine. Diff the working test against the failing one line by line.
The failing test never called filterColor.end(), so the hook never finalized. Lesson: check begin/end pairing before theorizing — and always shrink the repro first.
